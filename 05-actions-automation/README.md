# 05 — Actions & Automation

## Objective

Use GitHub Actions as a safe, observable automation layer for repository events, validation, publishing, scheduled work and controlled hand-offs to external services or AI agents.

## The Core Mental Model

```text
event
→ workflow
→ job
→ runner
→ steps
→ output / status / artifact / deployment / API action
```

An Action can be completely deterministic. **Automation does not automatically mean AI.**

```text
GitHub Action
= event-driven automation engine

AI agent
= reasoning/execution system that may be launched by, run inside, or operate independently of Actions
```

## Why This Matters to an Operator

Actions lets GitHub move from a passive record of work to an active control plane.

Useful categories include:

- test and validation;
- linting and formatting checks;
- security checks;
- build automation;
- Wiki/Pages publishing;
- release publishing;
- scheduled audits;
- Issue/PR triage;
- deterministic dispatch to coding agents;
- bounded AI inference;
- deployment orchestration.

The operator’s job is not to write YAML for its own sake. The job is to decide **which repeated rule deserves automation, what permissions it needs, and what evidence proves it worked**.

## Workflow Files

Workflows normally live under:

```text
.github/workflows/*.yml
```

A workflow normally defines:

- `name` — human-readable workflow name;
- `on` — trigger/event;
- `permissions` — workflow token scope;
- `jobs` — units of work;
- `runs-on` — runner type;
- `steps` — actions/commands executed in order.

## Trigger Thinking

Think in events before thinking in implementation.

| Need | Common trigger |
| --- | --- |
| Validate proposed change | `pull_request` |
| React after merge/push | `push` |
| Respond to new/changed work | `issues` / `issue_comment` |
| Explicit operator action | `workflow_dispatch` |
| Scheduled audit | `schedule` |
| Publish release | release/tag/version event pattern |
| Reuse workflow | `workflow_call` |

Course examples include:

- Wiki publishing after approved source changes;
- GitHub Pages deployment;
- release publishing;
- Copilot CLI inference from an Issue;
- Codex/Claude/Copilot deterministic dispatch workflows;
- Gemini CLI/API benchmark workflow.

## Jobs, Steps and Runners

### Job

A job is a group of steps executed on a runner.

### Step

A step can:

- run shell commands;
- invoke a reusable GitHub Action;
- inspect repository context;
- call APIs;
- create artifacts;
- publish output.

### Runner

The runner is the machine/environment that executes the job.

Common models:

- GitHub-hosted runner;
- self-hosted runner;
- specialised larger/managed environments where applicable.

The runner choice affects security, filesystem/network access, cost and available tooling.

## Permissions: Two Different Layers

A frequent misconception is:

```text
Allow all actions and reusable workflows
= workflow can do anything
```

That is false.

Separate:

```text
Actions source policy
= which actions/reusable workflows are allowed to run

workflow permissions
= what the workflow's GITHUB_TOKEN may do
```

Use least privilege.

Example:

```yaml
permissions:
  contents: read
  issues: write
```

Do not grant `contents: write`, `pull-requests: write`, `actions: write` or other permissions merely because they might be useful later.

## Secrets and Credentials

A secret is a secure storage interface for a **real credential**.

```text
secret name
= repository lookup key

secret value
= actual token/key generated by GitHub or another service
```

Do not invent a password and assume it becomes an API credential.

### Course example

The repository uses:

```text
AGENT_DISPATCH_TOKEN
```

for a real user-authorised GitHub credential used by selected dispatch workflows.

A workflow can map the stored secret to a runtime variable expected by another tool:

```yaml
env:
  COPILOT_GITHUB_TOKEN: ${{ secrets.AGENT_DISPATCH_TOKEN }}
```

Therefore:

```text
stored secret name
≠
runtime environment-variable name
```

Never print secrets. Treat logs, PRs and Issue bodies as public/untrusted surfaces unless the repository is deliberately private and access-controlled.

## Deterministic Automation vs Agentic AI

Use the four-layer model:

```text
1. CONTROL SURFACE
   human / ChatGPT Web / GitHub UI

2. TRIGGER + DETERMINISTIC AUTOMATION
   Issue / push / workflow_dispatch
   → GitHub Actions

3. AGENTIC EXECUTION
   Copilot / Codex / Claude / Gemini / Jules / other worker

4. DELIVERY + EVIDENCE
   branch / commit / PR / comment / check / artifact / deployment
```

This is critical for debugging.

A successful workflow run does not prove an AI agent executed.

## Proof Ladder for Automation

Verify each boundary:

```text
trigger created
→ workflow run exists
→ intended job starts
→ intended step is reached
→ credentials are present
→ authentication succeeds
→ external/AI request accepted
→ downstream work becomes observable
→ output is delivered
```

### Failure classification

| Evidence | Likely layer |
| --- | --- |
| no run | trigger/workflow definition |
| job skipped | condition/filter |
| secret empty | secret scope/name/setup |
| HTTP 401 | invalid/expired credential |
| HTTP 403 | authenticated but forbidden by permission/plan/policy |
| agent accepted but no output | downstream runtime/session |
| PR exists but checks fail | implementation/CI |
| deploy succeeded but website wrong | publishing/entry/UX layer |

## Actions as a Command Bus

One powerful pattern is:

```text
ChatGPT Web / human
→ create/refine Issue
→ deterministic GitHub event
→ Action dispatches worker
→ worker produces governed output
```

This lets the human keep a simple front door while preserving a durable GitHub execution trail.

Do not add an Action if native direct assignment already solves the problem cleanly. Automation should remove repeated friction, not create orchestration for its own sake.

## Safe Workflow Design

Before merging an Actions change, review:

1. trigger scope;
2. permissions;
3. secrets consumed;
4. untrusted input handling;
5. external actions/providers;
6. branch/PR write behaviour;
7. failure behaviour;
8. retries/idempotency;
9. logs and observability;
10. whether the workflow can merge/deploy/destructively mutate state.

For AI workflows, also ask:

- What context reaches the model?
- What can the model write directly?
- Can deterministic code own sensitive writes instead?
- Does the first run stop before merge?

## Hands-On Exercise 1 — Read an Existing Workflow

Choose `.github/workflows/publish-wiki.yml` or another existing workflow and explain:

- trigger;
- permissions;
- runner;
- jobs;
- steps;
- credentials/secrets;
- expected output;
- evidence you would inspect after a run.

## Hands-On Exercise 2 — Create a Bounded Automation

Create a small workflow that performs a safe, deterministic task such as validation or a text-only report.

Requirements:

1. governing Issue;
2. least-privilege `permissions:`;
3. narrow trigger;
4. clear failure behaviour;
5. no secret logging;
6. PR review before merge;
7. inspect the resulting run/jobs/steps/logs.

## Hands-On Exercise 3 — Diagnose a Failure

Given a failed run:

1. identify trigger;
2. identify first failed/skipped step;
3. classify failure layer;
4. inspect the minimum relevant logs;
5. propose the smallest fix;
6. rerun only what is justified;
7. record durable evidence.

## Mastery Check

A learner should be able to explain:

1. workflow vs job vs step vs runner;
2. event trigger vs manual dispatch;
3. Actions source policy vs workflow token permissions;
4. secret name vs credential value;
5. deterministic automation vs agentic AI;
6. why a green workflow does not prove the intended downstream outcome;
7. how to find the first failing layer;
8. when Actions is useful and when it is unnecessary orchestration.

## Evidence Required for Mastery

At least one learner-operated workflow where the learner can:

- explain the YAML;
- trigger it intentionally;
- inspect run/job/step evidence;
- diagnose one failure or explain why the successful result proves the intended outcome;
- justify the permissions.
