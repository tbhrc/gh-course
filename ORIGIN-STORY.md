# The Origin Story — From Learning GitHub to ARC

## The beginning

GitHub Course started because David Potgieter had a simple hunch: **GitHub was much more powerful than the way he was currently using technology in the business.**

The original objective was not to design a company-wide operating system. It was to learn GitHub properly.

That distinction matters, because the architecture did not arrive as a theoretical blueprint. It emerged through a repeated loop:

```text
learn one capability
→ understand why it matters
→ test it in a real repository
→ use it on a real business problem
→ keep what works
→ change the operating model
→ learn the next capability
```

## Learning became migration

Very quickly, the course stopped being passive education.

As David learned how GitHub Issues, branches, Pull Requests, Projects, Actions, agents and repository governance worked, those capabilities were immediately applied to real TBHRC and iMPLEMENTAi work.

That changed the question from:

> "How does GitHub work?"

into:

> "Why are we not operating this way already?"

The migration away from FolderDesk therefore began **while the learning was still happening**. GitHub Course became both classroom and proving ground.

Each useful concept moved from lesson to live operation:

```text
Issue
→ not merely a ticket
→ durable work/control object

Pull Request
→ not merely code review
→ governed integration boundary

GitHub repository
→ not merely source code storage
→ owner of durable operating truth

Skill
→ not another SOP file
→ reusable HOW for human + AI work

AI agent
→ not useful in isolation
→ reasoning connected to Skills, tools, permissions and current owner truth

Actions / runners
→ not generic automation
→ deterministic execution and runtime capability

Research
→ not a link collection
→ discovery/proving layer for the next capability improvement
```

## The key discovery

The most important lesson was not a single GitHub feature.

It was that **infrastructure compounds**.

A small operational problem can expose a missing capability. Research can reveal an existing tool. A bounded test can prove that tool. Once integrated correctly, the improvement becomes available to many agents and workflows rather than solving only the original symptom.

The system therefore evolved toward:

```text
problem
→ reusable method
→ correct owner
→ authorised agent
→ available tools
→ safe execution
→ verification
→ durable evidence
→ reusable learning
```

And when the problem reveals a broader capability gap:

```text
local symptom
→ Research
→ workflow
→ reusable capability
→ platform/system
→ compare existing solutions
→ test
→ benchmark
→ promote only when proven
```

## From FolderDesk to the current architecture

FolderDesk was an important predecessor. It proved the value of structured AI-accessible operations, connectors, files, Skills and repeatable workflows.

But the GitHub learning journey exposed a stronger operating model:

- GitHub as the durable human + AI operating desk;
- Issues and PRs as native work and change-control objects;
- `tbhrc/skills` as the reusable HOW / central nervous system;
- domain repositories and specialist systems as owners of their own truth;
- `tbhrc/research` as the external discovery and proving layer;
- authorised AI agents as the normal reasoning/execution layer;
- `tbhrc/ai-engine` as a narrow privileged runtime bridge for VPS, isolated runners and local execution that normal tools cannot safely reach;
- verification and GitHub evidence as the completion standard.

The old `tbhrc/AOS` / Agentic Operating System and FolderDesk repositories remain historical evidence. They are not the current deployment canon.

## Why the Course must preserve this story

The sequence is itself a teaching method.

A future learner should not receive a giant finished architecture diagram and be told to memorise it. They should understand the problems each component solved and why the boundaries exist.

The Course therefore teaches ARC in dependency order:

```text
GitHub mental model
→ durable work
→ safe change
→ portfolio coordination
→ deterministic execution
→ security/governance
→ AI agents + Skills
→ Research + capability discovery
→ complete ARC operating loop
```

This preserves the original strength of the GitHub Course: **learn something useful, apply it immediately, and let real evidence shape the next layer.**

## The next chapter: ARC

The current ecosystem now needs a short name so humans and agents can refer to the same architecture without saying "the ecosystem" every time.

Working canonical codename:

# ARC

ARC is already present in the current canonical Human + AI Operations Map as the `ARC blueprint`. It is a clean name with no current `tbhrc/arc` repository collision and does not inherit the operational history attached to FolderDesk or the old AOS repository.

ARC is treated as the system/product name first. No forced acronym expansion is required.

The long-term split is:

```text
GitHub Course
= teaches why + how to understand and reproduce ARC

ARC repository
= maintains the portable deployment blueprint/package for reproducing the ecosystem

Live repositories/systems
= continue to own current business/product/runtime truth
```

## What reproducibility means

A future ARC deployment repository should make it possible to reproduce the architecture for another business or environment without copying TBHRC's live data or secret values.

It should maintain a versioned, testable description of:

- required component types;
- canonical repository/capability relationships;
- bootstrap sequence;
- Skills distribution model;
- agent/tool/runtime interfaces;
- Research promotion loop;
- configuration contracts;
- secret names/placeholders and provisioning boundaries;
- deployment profiles;
- verification and health checks;
- upgrade/migration procedures;
- backup/restore/redeployment instructions.

That repository becomes the **safe harbour for reproducibility**.

The Course remains the place where a person learns to understand and operate what ARC deploys.

## The continuing principle

The origin story is not finished.

ARC should keep improving through the same loop that created it:

```text
operate
→ encounter friction
→ think bigger
→ research
→ test
→ benchmark
→ integrate when proven
→ teach the improvement
→ update the reproducible blueprint
```

That is the method the Course must preserve for future students.
