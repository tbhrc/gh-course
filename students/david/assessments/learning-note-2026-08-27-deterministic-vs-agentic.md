# Learning Note — Deterministic Automation vs Agentic AI

**Student:** David  
**Date:** 27 August 2026  
**Related Issues:** #23, #24, #34, #38

## Starting observation

David noticed that after ChatGPT Web performed a GitHub operation, other work sometimes happened later without another manual instruction. He initially suspected that Codex, Claude or Gemini might already be executing in the background.

## Evidence audit

Repository evidence separated the actors:

- ChatGPT Web/GitHub connector created GitHub objects and repository changes.
- GitHub Actions automatically ran deterministic workflows after pushes/merges.
- `github-actions[bot]` produced comments and notifications.
- Pages and Wiki publishing jobs executed automatically.
- No Codex/Claude/Gemini benchmark branch, evidence file or PR had yet appeared.

## Breakthrough

David then articulated the key distinction himself:

```text
GitHub Action / workflow
can be deterministic automation

AI coding agent
is a separate agentic reasoning/execution layer
```

He recognised that a deterministic script only needs a trigger. ChatGPT Web can act as the control surface that creates that trigger, while GitHub Actions can either perform deterministic work directly or dispatch a separate AI agent.

## Applied architecture insight

David's desired operating model became:

```text
founder talks to ChatGPT Web
→ ChatGPT Web creates/refines Issue
→ ChatGPT Web fires GitHub trigger
→ deterministic Action dispatches worker
→ Codex / Copilot / Claude / Gemini executes
→ branch + PR + checks
→ governed merge / release
```

His specific judgement was that the founder should not have to manually open Codex for every task once the repository has been configured correctly.

## Authentication lesson

The first Codex dispatcher failed because `AGENT_DISPATCH_TOKEN` was missing.

David initially created an invented password as the secret value. The correction was:

```text
Actions secret
= secure container

secret value
= real credential generated by the external/authenticating service
```

He then generated a real fine-grained GitHub personal access token and stored it in GitHub.

Live workflow evidence subsequently showed:

```text
AGENT_DISPATCH_TOKEN: ***
```

proving that GitHub Actions received the real secret.

## Failure-layer reasoning

The dispatcher then reached GitHub's native coding-agent assignment endpoint but returned HTTP `403 Forbidden`.

This established another professional distinction:

```text
automation working
≠
authentication working
≠
agent entitlement/policy working
≠
agent execution proven
```

The course therefore moved from guessing to a layered evidence model.

## GitHub Copilot cloud-agent benchmark — Issue #38

A separate benchmark was then created specifically for GitHub's own Copilot cloud agent so its evidence would not be mixed with the Codex partner-agent test.

ChatGPT Web created the dispatch branch and marker:

```text
dispatch/copilot/38
→ .dispatch/copilot/38.md
→ push
→ Dispatch GitHub Copilot from GitHub
```

The first run proved:

```text
✅ dispatch target resolved as Issue #38
✅ user-authorised dispatch credential present
✅ PAT visible to Actions as ***
✅ request used copilot-swe-agent[bot]
✅ request included agent_assignment payload
✅ authenticated GitHub API request reached the assignment endpoint
❌ GitHub returned HTTP 403 Forbidden
```

Exact response:

```json
{
  "message": "Forbidden",
  "documentation_url": "https://docs.github.com/rest/issues/assignees#add-assignees-to-an-issue",
  "status": "403"
}
```

No Copilot agent session, Copilot-authored branch, commit or Pull Request was created.

The evidence therefore proves the deterministic command bus and authentication path, but **does not prove agentic Copilot execution**. The remaining boundary is account/repository plan, policy, entitlement or permission.
