## Demonstrated Knowledge

### Git and GitHub

David's starting mental model was that Git is the local repository on the hard drive and GitHub is the cloud location where that repository is pushed and stored.

**What this demonstrates:** correct practical understanding that local Git work can exist independently and can be pushed to GitHub.

**Correction required:** Git is the version-control system, not the local repository itself. A Git repository may exist locally or remotely.

### Repository

David described a repository as a container or folder holding files and subfolders, similar to a small hard drive or storage box.

**Assessment:** useful and operationally correct mental model.

### Commits

David understood commits as version-control checkpoints that allow history and rollback. He correctly recognised that many smaller changes are more useful than one giant change because individual changes can be inspected or undone.

His initial rule was approximately "one commit, one feature".

**Refinement:** one commit should ideally represent one logical change; a feature may contain several commits.

**Correction required:** committing does not send work to GitHub. A commit records history in Git; `push` sends commits to a remote such as GitHub.

### Branches and Merging

David described a branch as an isolated sideline for developing a feature rather than working directly on `main`, followed by merging the completed work back into `main`.

**Assessment:** correct practical foundation.

### Clone / Pull / Push

David understood:

- `clone` as making a local copy of an existing repository;
- `pull` as updating the local copy from the remote;
- `push` as sending local repository changes to GitHub.

**Assessment:** broadly correct.

### `main`

David understood `main` as the normal default branch and recognised `master` as an older alternative name seen in some repositories.

### `.gitignore`

David understood that generated/runtime/dependency or local operational files may need to be excluded from tracking and that secrets should not be uploaded.

**Critical correction:** `.gitignore` is not a security mechanism. If a secret has already been committed, ignoring the file later does not remove the secret from Git history.

### Diffs

David has actively used diffs/work-tree history and understands that a diff shows how files changed from one commit/state to another.

**Assessment:** practical demonstrated capability and one of his stronger starting areas.

## Major Knowledge Gaps Identified

### Pull Requests

David initially described a Pull Request as pulling work from GitHub to local Git.

**Baseline status:** misconception / beginner.

**Required concept:** a Pull Request proposes merging changes from one branch into another and provides the review, diff, checks, discussion and approval surface around that change.

David has seen agents use Pull Requests but has not meaningfully operated them manually.

### Issues

David understood a GitHub Issue as basically a task tracker.

He had never created an Issue operationally before this diagnostic and did not yet understand the broader lifecycle linking Issues, branches, commits, Pull Requests, automation and closure.

### Labels, Milestones, Assignees and Projects

David could logically infer their probable meanings from their names but reported no operational experience using them.

### GitHub Actions

No operational knowledge at baseline.

### GitHub Projects

No operational knowledge at baseline.

### Wiki / Knowledge Architecture

No GitHub Wiki experience. David associated "wiki" with hyperlinks, backlinks and a possible memory/knowledge layer, but had not used GitHub Wiki and did not know its actual role.

### Revert vs Reset

No baseline knowledge.

### `git blame`

No baseline knowledge.

### Concurrent Agent Changes / Merge Conflicts

David did not know what happens when multiple agents modify the same file simultaneously.

### Releases and Professional Versioning

David has worked with numbered software versions such as `3.30`, `3.31`, `3.32`, but had not yet demonstrated operational knowledge of GitHub Releases, tags or release workflows.

### AI Agents + GitHub

David uses Claude Code, Codex, ChatGPT and GitHub Copilot in AI-assisted development workflows and enjoys VS Code as an operating environment.

At baseline he had not used GitHub-native agent workflows where an Issue can become assigned work that flows through a branch, commits, tests, Pull Request, review and merge.
